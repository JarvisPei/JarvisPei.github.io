Fast Decisions, Useful Agents

Lessons from putting NeoHorse-Jev inside the loop.

Zehua Pei · Experiments with the NeoHorse Team

In my earlier essay, Where Jev Fits in an Agent Loop, I described decision models as programmable semantic operators: small components that answer questions software cannot easily settle with rules. Is this passage relevant? Which worker should handle this request? Does the current evidence justify moving on?

The interface takes an observed state and a set of typed questions, then returns choices or scores that code can consume. The attraction is to make a semantic judgment callable without asking a generator to write and explain another answer.

That remains an appealing interface. While building NeoHorse-Jev, we found that a model could return a typed decision quickly, and that specialization could improve a narrow skill. The next question was whether those properties would make an agent more useful.

So we moved from isolated judgments to interventions: let a decision stop a tool loop, skip a verification call, or produce a set of topic assignments. A useful decision component has to improve the work around it. Its own response time is only one part of that story.

The distinction became clearest when an agent finished faster by leaving something unfinished.

1. Completion is a consequence, not just a label

Consider a request involving several files: preserve one, move another, remove an obsolete directory, and make sure the retained contents match. “Is everything done?” looks compact at the API boundary. Answering it requires accounting for every obligation.

Breaking the request into a checklist helped. But it helped the ordinary main-model baseline too. Some of what initially looked like a benefit from adding a decision model was a benefit from making the task and evidence explicit.

We then held the facts about one obligation fixed while changing progress on the others. Some local judgments changed with that unrelated progress. A narrower evidence view corrected several observed errors. Yet in a later executable counterexample, the model confidently judged different file contents to match. That answer allowed the controller to end the task. An exact program check rejected it.

Checking exact contents, permissions, or whether a command actually ran belongs in code. A model can help interpret “relevant” or “sufficient,” but should not replace an available exact check merely because both can be phrased as yes-or-no questions.

Recognizing a condition and enforcing it are different jobs, too. A model may identify a forbidden operation while the acting agent still performs it. The host must enforce permissions and limits.

The decision API makes a judgment explicit. The surrounding program still decides what it can authorize.

2. A probability needs a question with a complete meaning

A decision interface encourages short questions. That can hide a surprisingly large amount of specification.

In a multi-label message experiment, we asked whether messages belonged to categories such as aid, infrastructure, and weather. Each also had an “other” category. “Other aid” only makes sense relative to the named aid categories. If those definitions live elsewhere, an independently evaluated question may not contain enough information to establish the distinction.

Our specification had exactly this problem: some residual-category questions referred to other categories without listing them. The ordinary LLM received the full taxonomy, while the decision questions were not self-contained. This was an input-contract problem, and a reason not to attribute the entire quality difference to model capacity.

Making the definitions longer was not a general fix. In a small development comparison, explicitly listing the categories corrected several intended distinctions but introduced more unrelated positives. More complete instructions and better predictions did not move together.

The application must supply the information needed to interpret each question. The model must still use that information correctly. Adding prose addresses the first responsibility; it does not automatically satisfy the second.

The same distinction matters for confidence. In a source-checking task, the model approved a claim that restoring a biological mechanism impaired regeneration, although the abstract said restoration improved it. The support score was about 0.96. Later held-out source checks produced another clear high-confidence direction error. Selecting a threshold on separate calibration data changed shortcut coverage without removing that semantic mistake.

The practical question is therefore not simply whether the score is high. It is what error rate the policy produces on this kind of decision, and what happens when it is wrong.

3. Count the work after the decision

We tested a cascade: a decision model could directly accept sufficiently high-scoring source support; otherwise, the request went to the main LLM.

This arrangement can save work. In three short repeated runs on the same 48 claim–source pairs, it reduced main-model calls from 48 to 33 per run. Pooled mean latency fell by about 18%. But total network requests rose from 48 to 81 per run, the 95th-percentile latency was worse in every run, and one round had more unresolved fallback timeouts.

Every request pays for the decision call. Only the shortcut subset avoids the main-model call. The rest pay for both. A favorable average does not mean the slower requests improve, and fewer main-model calls do not establish a lower total bill.

We also connected the cascade to an actual retrieval loop: search a corpus, inspect abstracts, refine the search, and submit a verdict with a source. It made fewer main-model calls and had a lower observed mean runtime. It also introduced a clear semantic error that the ordinary agent avoided. Our initial aggregate score obscured the difference because some other failures concerned explanation length. Separating substantive correctness from that formatting requirement exposed the tradeoff.

The useful unit is a completed outcome. That requires accounting for judgment, fallback, extra searches, retries, and repair. It also requires distinguishing a wrong answer from a request that never returns an answer.

This is not a demand for zero mistakes. A recoverable extra search and an incorrect final approval have different costs. Whether the component helps depends on which mistakes it introduces and what work it removes.

4. There is a real speed–quality tradeoff

We next tried a workload that naturally needs several judgments: topic assignment on historical messages in the public Disaster Response Messages dataset. The categories came from an existing message-coding task; we did not multiply questions to make batching look useful.

The ordinary LLM returned one compact list of positive labels. Our NeoHorse-Jev-4B service answered 35 typed questions in three sequential requests, because the deployed interface allowed at most 16 questions per call. All three requests counted toward latency.

On a fresh 96-message confirmation batch, we observed:

Missed positive topic assignments6467

These compare two hosted services: a provider-declared Haiku 4.5 endpoint and our 4B decision model. They do not isolate architecture or hardware. The input-definition issue above and limitations of the historical annotations remain relevant. This was offline label evaluation, not real emergency dispatch or reviewer productivity.

The faster service produced substantially more extra labels at similar recall. If each label creates a queue entry, additional review can matter more than a second saved at inference. If labels are only inexpensive suggestions, the balance may differ. That is a workload decision, not something F1 or latency settles alone.

One improvement came from ordinary software. We required each of three residual labels to have its corresponding predicted parent: “other weather,” for example, required “weather-related.” We fixed the rule before the new batch and applied it to both models' unchanged outputs.

For Jev, extra assignments fell from 237 to 216 and micro F1 rose from 48.65% to 50.44%. Missed assignments stayed at 67. The same rule removed four extra labels from the ordinary LLM. It added no model calls.

This modest improvement repeated on new messages. It did not repair model understanding or close the quality gap; a wrong parent prediction could still suppress a valid label. Its value was to make an application constraint explicit rather than ask the model to infer it every time.

5. Specialization needs an operating scope

Our earlier controlled experiments showed that adapting a model to a form-action task could improve completion, and that specialization could improve judgments on a narrow family of constraints. These remain reasons to be interested in customization.

They also showed why a specialist needs a defined scope. After one constraint adaptation, accuracy on our general decision subsets changed relatively little, while probability-quality measures worsened. A policy relying on scores can change even when most top-choice answers stay the same.

I would distinguish three mismatches. Evidence may be missing. The question or acceptance criterion may be wrong. Or the model may lack the semantic skill the application needs. Training can address the third, but cannot supply evidence the runtime never observes or enforce a permission rule the software ignores.

Customization becomes most useful once a recurring decision has a stable meaning, feedback, and a clear place in the application. A specialist need not become a better general assistant. It does need to improve the task it is assigned.

6. Where the community evidence points

Some recent reports get closer to the system-level question than a fast classification demo.

The Jev Gate long-session pilot rebuilt two real features from a private codebase in paired 17-turn coding sessions. The author reported total cost falling from about $42.81 to $19.65, with the same combined quality score of 21/23. The tasks traded a small quality advantage in opposite directions. The plugin combined worker delegation, model selection, and context compaction, and each task had only one pair of runs. It is a positive lead for changing how long sessions allocate work, not a measurement of the decision model's isolated contribution.

Other reports show why the alternative matters. In LLM Gateway's routing pilot, routing was cheaper than a fixed premium model, but a fixed mid-priced model was cheaper still and passed slightly more tasks. pi-jev's validation record showed substantial context reduction, while local retrieval outperformed hosted Jev-assisted retrieval on one small paired fixture study. Better allocation and retrieval can help without requiring a decision model at every branch.

A broader study of Jev in agent workflows reached a related finding across embodied and mobile tasks: decision-level savings did not transfer uniformly to successful delivery. Recovery and premature completion affected the result. These are other researchers' systems and models, not measurements of NeoHorse-Jev, but they reinforce the need to follow a decision through to its consequences.

The common theme worth pursuing is repeated, bounded work with an observable outcome. A component earns its place when it improves that outcome relative to a reasonable alternative: a rule, a fixed model, local retrieval, or a different division of work.

What I would ask before adding another decision model

I still like the idea of a resident semantic component. Making judgments callable exposes questions otherwise buried inside a long model response. It creates a place to specialize, inspect errors, and change policy independently of generation.

I would now begin with the application rather than the endpoint:

  • What recurring decision does the workflow already need?
  • Does the component see enough information to answer it?
  • What changes after its answer, and what does a mistake cost?
  • Does the complete workflow improve against its simplest credible alternative?

“Advisory only” is not an automatic answer to the third question. We tried ranking real code-repair trajectories for review and did not find a useful failure-prioritization signal. A suggestion still needs to help someone decide where to spend attention.

We have paused this round rather than keep searching for a favorable small result. The experiments leave implementation lessons and bounded positive signals, but not a workflow we can yet recommend as a stable win for our deployed model.

My original view of decision models as semantic operators survives. The additional requirement is that the operator must earn its place in the program. A fast answer is useful when it helps the system deliver better work, spend less effort, or recover sooner—not merely when it returns before the generator does.
